## What this is
The Autonomous Growth OS is an autonomous growth intelligence system that continuously researches markets, manages advertising experiments, measures real business outcomes against first-party truth, learns causally from its actions, and improves its own strategy—while never holding the credentials that would let it spend money unchecked. It is not a chatbot around Google Ads, not a cron job asking an LLM what to change, not a dashboard producing recommendations. It is an autonomous growth scientist + performance marketer + measurement platform + bounded self-improving software system that executes: Observe reality → verify measurement → research the market → identify the highest-value bottleneck → form falsifiable hypotheses → simulate/risk-check → experiment → execute through bounded capabilities → wait for mature evidence → measure downstream business impact → update beliefs → improve its own methods → search for the next frontier → repeat indefinitely. The system begins with paid acquisition but reasons across the full growth stack: market → demand → positioning → ad/creative → click → landing page → lead/cart → qualification/checkout → sales/purchase → customer → margin → retention → LTV. Three compounding loops drive it: business optimization (observe → diagnose → hypothesize → experiment → execute → measure → learn), market understanding (research → discover demand/objections/trends → create hypotheses → test in reality → update knowledge), and system self-improvement (evaluate own decisions → discover weakness → reproduce → create candidate → replay + adversarial eval → shadow/canary → promote or reject). The first release is a simulator + read-only Google Ads integration + decision journal + shadow mode, proving the architecture before any real credential touches the system.

## Stack
TypeScript 5.6+ (Node.js 22 LTS) for API/BFF, Policy Kernel, Executor, Temporal workers, event ingestion, admin UI (React 19 + Next.js 15). Python 3.12+ for ML/statistics. PostgreSQL 16+ with pgvector 0.8+ (Cloud SQL). Temporal Cloud. GCP (Cloud Run, Pub/Sub, Secret Manager, KMS). Browserbase + Playwright. Anthropic Claude API. Google Ads API v22, Meta Marketing API.

TypeScript for the core because the spec describes entities in TypeScript types, the Policy Kernel and Executor are deterministic systems where type safety prevents expensive mutations, Temporal has a mature TypeScript SDK, and the admin UI is React. Python for ML/statistics because the ecosystem (NumPy, SciPy, pandas, scikit-learn, PyMC) is unmatched for quantitative modeling. PostgreSQL + pgvector because Phase 1 of the spec says it is enough, Cloud SQL supports pgvector, and it handles operational state + embeddings in one database. Temporal Cloud for durable multi-day workflows (experiments, research, evaluation, self-improvement) with crash recovery; Google Cloud Workflows is less suited to Python-heavy strategy logic. GCP (Cloud Run services/worker pools/jobs, Cloud SQL, Pub/Sub, Secret Manager, KMS) because the spec designs around these services and OIDC from GitHub Actions. Browserbase for managed browser research with Playwright as fallback. Anthropic Claude as primary LLM with a ModelRouter abstraction preventing vendor lock-in per invariant 0.1.12. Google Ads API v22 first (query intent interpretable, reporting strong, experiments native, keyword planning primitives, downstream conversion support, less creative complexity than Meta). Docker + GitHub Actions for CI/CD with OIDC to GCP.

Rejected:
- **Kubernetes** — The spec explicitly states 'do not deploy Kubernetes early' in section 20. Cloud Run services/worker pools/jobs are sufficient for the cost-sensible alpha, scale to zero, and avoid the operational complexity of cluster management before the system has proven its architecture.
- **BigQuery from day one** — Section 21 states 'Phase 1 — PostgreSQL is enough' and to add BigQuery only when event volume grows. Starting with BigQuery adds cost and complexity before the system has proven it can manage real spend safely; PostgreSQL + pgvector handles operational state, research, memory, actions, experiments, and modest event volume.
- **Python for the core platform** — The spec describes entities in TypeScript types, the Policy Kernel and Executor are deterministic systems where type safety is critical, and Temporal's TypeScript SDK is more mature than the Python SDK for the workflow patterns described (durable multi-day workflows with timers, signals, crash recovery). Python remains the right choice for ML/statistics where the ecosystem is unmatched.
- **Node.js 24** — Node.js 22 is the current LTS release (confirmed in the CI config at .github/workflows/ci-verify.yml line 47: 'node-version: 22'). Node 24 is current but not LTS; LTS provides longer support and stability for a production system managing real money.
- **AWS or Azure** — The spec explicitly recommends GCP: Cloud Run services/worker pools/jobs, Cloud SQL PostgreSQL with pgvector, Pub/Sub, Scheduler, Secret Manager, KMS, Storage, Logging/Monitoring, Artifact Registry. The spec also describes OIDC from GitHub Actions to GCP. Switching to AWS or Azure would require rewriting the deployment topology and losing the Cloud Run worker pool pattern the spec designs around.
- **A single frontier model for everything** — Section 17 explicitly states 'do not use one expensive frontier model for everything' and requires a ModelRouter. Extraction tasks should use fast/cheap models, strategy requires high-reasoning, risk critique needs an independent strong pass, and coding/self-improvement uses a coding agent in a sandbox. A single model would violate the independence requirement for risk critique and waste cost on tasks that do not need frontier capability.

## Architecture
Monorepo with zone-based permissions (GREEN autonomous candidate / YELLOW PR only / RED mandatory code-owner review / BLACK inaccessible) initially, splitting into separate repositories for policy_kernel, executor, and infrastructure before enabling broad self-modification in production. The API/BFF is the entry point for the admin UI and external webhooks; it authenticates requests, routes to domain services, and never holds ad mutation credentials. The Policy Kernel is a small deterministic system with no LLM that evaluates ActionIntents and issues signed ActionCapabilities; it is the only service that reaches the capability-signing key via KMS. The Executor validates signed capabilities and performs typed mutations against ad platform APIs; it is the only service with ad write credentials. Temporal Cloud orchestrates durable multi-day workflows (experiments, research, evaluation, self-improvement) with workers in Cloud Run worker pools. Event ingestion receives first-party measurement events and provider webhooks, normalizes them, and publishes to Pub/Sub. Research, strategy, and analysis agents run as Temporal activities, calling the ModelRouter for LLM inference and accessing memory via hybrid retrieval (SQL for structured queries + pgvector for semantic search). The simulator (fake Google Ads, fake Meta Ads, synthetic business) runs as a standalone service for development and testing, providing a safe environment to build autonomous logic before any real credential. All services communicate via typed interfaces; no service reaches another's database directly. OpenTelemetry traces every agent and action: scheduler/event → workflow → state snapshot → model call → memory retrieval → tool call → proposal → critic → policy → executor → provider → reconciliation → evaluation.

### Modules
- `apps/api` — The API/BFF: authentication, routing, request validation, webhook receivers. Never holds ad mutation credentials.
- `apps/admin` — The admin UI: React 19 + Next.js 15. Dashboards for decisions, experiments, research, memory, actions, audit. Approval UI for high-risk actions.
- `services/policy_kernel` — The Policy Kernel: evaluates ActionIntents against guardrails, issues signed ActionCapabilities. The only service that reaches the capability-signing key via KMS. No LLM.
- `services/executor` — The Executor: validates signed capabilities, performs typed mutations against ad platform APIs. The only service with ad write credentials. No strategy, no LLM.
- `services/event_ingest` — Event ingestion: receives first-party measurement events (POST /v1/events) and provider webhooks, normalizes them, publishes to Pub/Sub. Idempotent consumers.
- `workers/temporal` — Temporal workers for all workflow types: strategy (Growth Director, tactical optimizer, growth strategist), research (Research Planner, Market Research Agent), integrations (Google/Meta sync, CRM sync), evaluation (experiment evaluation, action evaluation, self-audit).
- `agents` — All agent implementations: Growth Director, Research Planner, Market Researcher, Customer Intelligence, Performance Analyst, Funnel Analyst, Creative Strategist, Hypothesis Generator, Risk Critic, System Auditor. Each calls the ModelRouter for LLM inference.
- `integrations/google_ads` — Google Ads API adapter: read campaigns/ad groups/ads/keywords/search terms/budgets/conversions/metrics/change history; keyword planning; experiments; Data Manager API for offline conversions. Write via Executor only.
- `integrations/meta_ads` — Meta Marketing API adapter: read campaigns/ad sets/ads/creatives/Insights/budgets/conversions; Ad Library research. Write via Executor only. Behind a versioned adapter.
- `integrations/browser` — Browser research: Browserbase for managed production browsers, Playwright as deterministic fallback. Prompt-injection boundary: external content is untrusted data. Isolated sessions, ephemeral, no ad secrets, domain allowlists, restricted egress.
- `integrations/llm` — ModelRouter abstraction: supports Anthropic Claude API (primary) with interface for multiple providers. Routes by task type: extraction (fast/cheap), strategy (high-reasoning), risk critique (independent), coding (sandbox). Versions provider/model/prompt/tool catalog with every decision.
- `domain` — Core domain types: Money (integer minor units, never float), Policy (ActionIntent, ActionCapability, PolicyDecision, guardrails, autonomy, kill switches, circuit breakers), Experiments (registry, arms, exposures, metrics, evaluations), Evidence (EvidenceRef, hierarchy Tier A–E, Learning schema with scope/evidence/confidence/status).
- `data` — Database layer: models (identity/tenancy, goals/policy, integrations, ads, measurement, market, intelligence, experiments, actions, memory, agents, health, audit), repositories (type-safe access, query builders, migrations), migrations. Raw vs derived separation: never overwrite raw source truth.
- `ml` — ML/statistical services in Python: maturity modeling (MatureMetric with maturity score, lag hours, policy bands), anomaly detection (spend acceleration, tracking loss, landing-page failures), forecasting (marginal spend curves, saturation, seasonality, response curves), causal inference (A/B, Bayesian, DiD, synthetic controls, uplift, bandits), calibration (prediction accuracy evaluation).
- `simulator` — Fake providers and synthetic business: fake Google Ads adapter, fake Meta Ads adapter, synthetic business (funnel, delayed conversions, seasonality, saturation, lead-quality variation, external changes, API failures, tracking outages). Required before any real credential per Phase 0.
- `evals` — Protected eval suite: frozen safety scenarios, adversarial tests, frozen historical datasets, promotion thresholds, historical replay, policy regression suite. The candidate must not be able to rewrite the exam it has to pass. BLACK zone, inaccessible to agents.
- `infra` — Infrastructure as code: Terraform for GCP (Cloud Run services/worker pools/jobs, Cloud SQL, Pub/Sub, Secret Manager, KMS, IAM, network), GitHub configuration (CODEOWNERS, protected branches, required checks, OIDC for GCP auth).

## Invariants
These hold for every ticket, whatever it asks for.

- Money is integer minor units (amount_micros BIGINT + currency CHAR(3)), never a float. Every arithmetic operation, database column, API field, and serialization format enforces this. The spec explicitly forbids float for money (§33.1, engineering rule 3).
- LLMs never directly possess advertising mutation credentials. Every external mutation passes through the Policy Kernel (which evaluates the ActionIntent and issues a signed ActionCapability) and then the Executor (which validates the signature, nonce, TTL, resource, constraints, and performs the typed mutation). The agent cannot modify the mechanism that defines what it is allowed to modify (§0.1.1, §0.1.2, §0.1.3, engineering rules 1, 2, 8).
- Recent metrics are never treated as mature when conversion delay can materially change them. Every metric carries a maturity score (0..1) with p50LagHours, p90LagHours, dataThrough. Policy bands enforce: <0.35 emergency-only actions, 0.35–0.70 observation + low-risk protective action, 0.70–0.90 moderate optimization, >0.90 eligible for strategic conclusions. Account-specific learning adjusts these thresholds over time (§0.1.9, §9, engineering rule 7).
- Every durable learning points to evidence. ## Commands
- `sdlc:verify` — `npm run sdlc:verify — TypeScript compilation (tsc --noEmit), linting (eslint), unit tests (vitest), policy regression suite (pytest for Python ML services), type checking for both TypeScript and Python (mypy). Runs in CI on every PR before any agent sees the diff.`
- `sdlc:serve` — `npm run sdlc:serve — Starts full stack via docker-compose: API (3000), admin UI (3001), Temporal dev server, workers, event ingestion, PostgreSQL + pgvector, simulator. QA boots app in compose mode.`
- `sdlc:seed` — `npm run sdlc:seed — Generates synthetic data for simulator: synthetic business, fake Google/Meta Ads accounts with campaigns, historical conversions with realistic lag, research observations. So QA never touches real records.`
- `sdlc:ready` — `npm run sdlc:ready — Health check endpoint (GET /health) that verifies: API is responding, Temporal dev server is reachable, PostgreSQL is up and migrations are applied, the simulator is initialized. Polled until it answers before the browser opens.`

Stubbed for now:
- sdlc:seed is 'exit 0' until the simulator and database schema exist, which is Phase 0 (issue #2)
- sdlc:serve does not start the simulator until the fake Google Ads and fake Meta Ads adapters exist, which is Phase 0 (issue #2)
- sdlc:verify does not run Python type checking until the Python ML services exist, which is Phase 1 (issue #3 or later)
- sdlc:serve does not start Temporal workers until the workflow definitions exist, which is Phase 0 (issue #2)

## Deploy
GitHub Actions for CI/CD: PR checks (verify, lint, unit tests, policy regression), security scanning, container builds, deploys to GCP via OIDC. GCP runtime: Cloud Run services (API, Policy Kernel, Executor, event ingestion), worker pools (Temporal workers), jobs (replay, research, backfill), Cloud SQL + pgvector, Pub/Sub, Secret Manager, KMS, Storage, Logging, Artifact Registry. Preview deployments: each PR gets temporary Cloud Run URL for QA; destroyed on merge/close. Cost-sensible alpha: services scale to zero when idle; one strategy worker, one integration worker; smallest Cloud SQL; managed Temporal Cloud; usage-based Browserbase and model spend. No Kubernetes. Separate prod/staging. OIDC from Actions to GCP.
